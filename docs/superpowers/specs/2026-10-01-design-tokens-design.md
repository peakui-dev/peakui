# Дизайн-токены PeakUI

Дата: 2026-10-01
Статус: дизайн утверждён, ожидает плана реализации

## Задача

У `@peakui/react` нет слоя токенов. Пока его нет, компоненты писать нельзя: стандарт
(`peakui-component-standards`) требует ссылаться на семантические токены, а ссылаться не на что.
Эту спеку блокирует весь остальной старт библиотеки.

Эталон — HeroUI v3, вендорен только для чтения в `/heroui`.

## Решения, принятые до спеки

Зафиксированы в обсуждении и здесь не переоткрываются:

1. **Имена токенов HeroUI 1:1, значения свои.** Выигрыш: вендоренный `heroui/` остаётся живым
   справочником, агенты угадывают имена правильно из тренировочных данных, миграция с HeroUI
   тривиальна. Цена принята осознанно — чужой словарь в своём продукте.
2. **Генеративный подход с первого дня** (не «руками, потом генератор»). Причина: рукописный
   `default` пришлось бы потом стыковать с генератором — либо подгонять математику под рукописные
   значения, либо принимать визуальный диф. Обе стыковки дороже, чем генерировать сразу.
3. **Источника истины по дизайну нет**, начинаем с нуля: спека задаёт и структуру, и стартовые
   значения.
4. **Типографика токенизируется** — у эталона её в токенах нет, и это его пробел, а не образец.

## 1. Слои и разрез «авторское / производное»

```
АВТОРСКОЕ (данные)      packages/styles/presets/<id>.ts
                        accent, grayChroma, radius, formRadius,
                        darkAccent?, semanticOverrides?, typography?
         │ генератор
         ▼
ГЕНЕРИРУЕМОЕ (CSS)      packages/styles/themes/<id>/variables.css
                        ├ примитивы    --white --black --snow --eclipse
                        ├ инварианты   --radius --spacing --border-width --disabled-opacity
                        │              --ring-offset-width --cursor-interactive --cursor-disabled
                        │              --tooltip-delay --skeleton-animation
                        ├ схемные      --background --foreground --surface(+secondary,tertiary)
                        │              --overlay --muted --default --segment --field-*
                        │              --border --separator --focus --link --backdrop
                        │              --surface-shadow --overlay-shadow --field-shadow --scrollbar-*
                        └ вычисляемые  --*-hover --*-soft --*-soft-foreground --*-soft-hover
                                       --background-secondary/tertiary --border-secondary/tertiary
                                       --separator-secondary/tertiary --field-hover --field-border-*

АВТОРСКОЕ (стабильное)  packages/styles/themes/shared/theme.css
                        @theme inline → --color-* --shadow-* --radius-* --ease-* --animate-*
                                        --font-* --text-* --font-weight-*
```

**Почему разрез именно здесь.** `theme.css` — публичная поверхность Tailwind: из неё берутся
`bg-surface`, `text-muted`, `rounded-xl`, `shadow-overlay`. Она пишется один раз и меняется только
при добавлении нового токена в набор. Генератор её не трогает никогда и производит только
`variables.css` конкретной темы. Следствие, которое и есть цель разреза: **добавление темы физически
не может сломать публичные утилиты**, потому что набор токенов фиксирован архитектурой, а тема
меняет лишь значения.

Каждый слой целиком попадает в оба блока схем (светлый и тёмный) — кроме примитивов и инвариантов,
которые объявляются один раз на `:root, :host`.

**`:host` обязателен рядом с `:root`.** Внутри shadow DOM `:root` не матчится, и без дубля
переменных там попросту нет.

## 2. Генератор

### Вход

```ts
type RadiusId = "none" | "extra-small" | "small" | "medium" | "large" | "extra-large";

// RadiusId → значение --radius. Вся шкала --radius-xs…4xl выводится из него
// множителями (0.25 / 0.5 / 0.75 / 1 / 1.5 / 2 / 3 / 4), как у эталона.
const RADIUS_BASE: Record<RadiusId, string> = {
  none: "0rem",
  "extra-small": "0.125rem",
  small: "0.25rem",
  medium: "0.5rem",
  large: "0.75rem",
  "extra-large": "1rem",
};

type SemanticSet = {
  accentForeground?: string;
  success?: {color: string; foreground?: string};
  warning?: {color: string; foreground?: string};
  danger?: {color: string; foreground?: string};
};

type ThemePreset = {
  /** Каталог темы и значение data-theme. */
  id: string;
  /** hex (`#rgb`/`#rrggbb`) или oklch; раскладывается в l/c/h. */
  accent: string;
  /** 0–0.03: сколько оттенка акцента несут нейтрали. */
  grayChroma: number;
  radius: RadiusId;
  formRadius: RadiusId;
  /**
   * Акцент для тёмной схемы. Автоматической инверсии НЕТ: без этого поля тёмная схема берёт светлый
   * акцент как есть. Это единственный механизм, а не фолбэк к выводу.
   */
  darkAccent?: string;
  /** Точные status-цвета, когда выведенные не подходят бренду. */
  semanticOverrides?: {light?: SemanticSet; dark?: SemanticSet};
  /** Стеки гарнитур темы → --sans / --mono. Шкала и веса темой не меняются (см. §3). */
  typography?: {sans: string[]; mono: string[]};
};
```

### Выход

На каждую тему: `themes/<id>/variables.css` (оба блока схем), `themes/<id>/index.css` (импортирует
`shared/theme.css`, свои переменные и свой `components/index.css`), `themes/<id>/components/index.css`
(пустой в `default` — крючок для прохода два, см. §4).

### Конвейер

```
разбор входа → схемные наборы → вычисляемые → ПРОВЕРКА КОНТРАСТА → эмиссия CSS
```

Проверка — **стадия конвейера, а не отдельный линтер**. Пресет, который не держит AA, роняет сборку.

### Проверка контраста

- Каждая пара `X` / `X-foreground`: коэффициент по WCAG 2.x (относительная яркость после
  oklch→sRGB), требование **≥ 4.5:1**.
- **Границы — только то, что опознаёт компонент.** WCAG 2.2 SC 1.4.11 требует 3:1 от визуальной
  информации, **опознающей компонент или его состояние**. Индикатор фокуса — именно она, поэтому
  `focus` проверяется против `background` и `surface` с порогом **≥ 3:1**.
  Декоративные `border`, `separator` и их уровни `-secondary` / `-tertiary` под критерий не попадают
  и порога не имеют: принудительные 3:1 дали бы жирный контур на каждой карточке, и эталон сидит на
  тех же ~1.2:1 ровно поэтому. **Следствие, которое надо знать:** если компонент использует
  `--color-border` как опознающую границу контрола, обеспечить 3:1 — обязанность компонента, и она
  покрыта требованием WCAG 2.2 AA в `peakui-component-standards`.
- Пара не прошла → генератор подбирает **светлоту** переднего плана (L в OKLCH): шаг 0.01, до 100
  итераций **в обе стороны**, хрома и тон не меняются, побеждает направление с наименьшим сдвигом.
  Обе стороны обязательны: на среднетоновом фоне проходят и светлее, и темнее, и какой именно —
  из фона не выводится. 100 шагов покрывают весь диапазон светлоты, 40 не покрывают. Каждая правка **сообщается** в выводе
  сборки — пара, исходная L, итоговая L, достигнутый коэффициент. Молча не правит.
- Поиск не сошёлся ни в одну сторону → ошибка сборки с указанием пары и лучшего достигнутого коэффициента.
  Это означает, что сам фон непригоден для текста, и решать должен человек, а не цикл.

**Почему это стоит генератора.** У эталона на этом месте порог `lightness > 0.65` и коэффициент не
считается нигде (`apps/docs/.../calculate-foreground.ts`). Важнее другое: **рукописный
`color-mix()` непроверяем** — в CSS его результат статически не измерить, а вычисляемых токенов около
сорока, все `-hover` и `-soft`. Генератор считает смешение сам, той же математикой, и проверяет
разрешённое значение. Руками эти сорок токенов остаются без проверки контраста навсегда.

### Полупрозрачность и измерение контраста

`mix(X p, transparent)` уменьшает **альфу**, а не светлоту: `accent-soft` это акцент с альфой 0.15, а
не бледный акцент. Отсюда два обязательных следствия:

1. Парсер и форматтер поддерживают альфу — `oklch(L C H / A)`.
2. **Полупрозрачный токен нельзя мерить напрямую.** Перед проверкой контраста он композитится по
   альфе на фон своей схемы — и на `surface`, и на `background`, — и держать порог обязан **худший**
   из двух: soft-плашка встречается и там, и там.
   **Композитинг идёт в гамма-кодированном sRGB**, потому что именно там CSS смешивает по альфе.
   Линейная интерполяция в OKLab завышает яркость до +50% на средней альфе: чёрный под 0.5 на белом
   даёт 0.125 вместо настоящих 0.214, то есть реальные 3.98:1 сертифицируются как 6.00:1.
3. **Список проверяемых пар выводится из набора токенов, а не пишется руками.** Каждый
   `X-foreground` проверяется против своего `X`. Рукописный список молча исключал все
   `*-soft-foreground`, и пресет с одним переопределением провозил текст плашек на 4.12:1 через все
   гейты.
4. **`muted` — вторичный текст** и встречается на каждом фоне набора, поэтому проверяется против
   **наименее выгодного** из них, а не против `background`. Проверка `accent-soft-foreground` против непосредственно
   `accent-soft` без композитинга даёт неверный коэффициент.

### Размещение и запуск

Генератор: `packages/styles/src/generator/`. Пресеты: `packages/styles/presets/`.
Запуск: `pnpm tokens:build`. **Вывод коммитится** — CSS должен потребляться без прогона сборки, диф
токена становится читаемым в PR, и VRT ловит непреднамеренные сдвиги.

### Стартовые значения `default`

```ts
export const defaultPreset: ThemePreset = {
  id: "default",
  accent: "oklch(0.52 0.20 275)",
  grayChroma: 0.006,
  radius: "medium",      // --radius: 0.5rem
  formRadius: "large",   // --field-radius: calc(var(--radius) * 1.5)
};
```

Акцент — индиго, осознанно отведённый от синего HeroUI (тон 253.8), чтобы система не читалась как
его копия. Светлота 0.52 выбрана не на глаз: при c=0.20 диапазон L 0.56–0.60 — мёртвая зона, где ни
светлый, ни тёмный передний план не берёт 4.5:1, и первая версия спеки стояла ровно в ней (0.58).
Ниже зоны выигрывает светлый текст, выше — тёмный; 0.52 даёт белому тексту 5.5:1. **Это единственное значение, которое ожидаемо изменится** после первого взгляда дизайнера;
правка — одна строка пресета, и в этом весь смысл генеративного подхода: архитектура от значения не
зависит. Нейтрали несут тон акцента на хроме 0.006 — тогда серые принадлежат палитре, а не выглядят
чужими.

## 3. Типографика

Типографика разрезается по тому же принципу, что и цвет: **что тема меняет — генерируется, что
фиксировано набором — авторское.**

| Группа                            | Где объявляется                      | Слой        |
| --------------------------------- | ------------------------------------ | ----------- |
| Стеки гарнитур `--sans`, `--mono` | `themes/<id>/variables.css`          | генерируемое |
| Маппинг `--font-sans`, `--font-mono` | `shared/theme.css` (`var(--sans)`) | авторское   |
| Шкала `--text-*` + парный `--text-*--line-height` | `shared/theme.css`  | авторское   |
| Веса `--font-weight-*`            | `shared/theme.css`                   | авторское   |

То есть гарнитура — ручка темы (Pro-тема меняет лицо), а шкала и веса принадлежат набору и одинаковы
во всех темах. Шкала в `shared/theme.css` использует парный синтаксис Tailwind v4: `--text-sm` рядом
с `--text-sm--line-height`.

Веса объявляются отдельными токенами потому, что Pro-тема меняет гарнитуру, а разные гарнитуры дают
одинаковый оптический вес на разных числах; тема переопределяет `--font-weight-medium`, не трогая
компоненты.

По умолчанию: **Inter** (sans) и **JetBrains Mono** (mono) — у обоих полноценная кириллица, оба
переменные. Моно с кириллицей нужен потому, что в примерах кода будут русские комментарии.
Альтернатива для отчётливо русского голоса — **Golos Text**. Покрытие глифов под конкретные задачи
проверяется отдельно, до фиксации.

Три решения, специфичных для кириллицы:

1. **`tracking-tight` на заголовках по умолчанию не ставим.** Это латинская конвенция: кириллический
   нижний регистр почти целиком живёт на x-height, выносных элементов мало, текст плотнее сам по
   себе, и поджатый трекинг бьёт по читаемости сильнее, чем в латинице. У эталона `tracking-tight`
   стоит на всех заголовках.
2. **Порог интерлиньяжа выше**, чем в системе под латиницу, по той же причине плотности.
3. **Запас на длину.** Русский текст примерно на 10–15% длиннее английского при том же содержании.
   Это бюджет для `min-width`, усечения и паддингов — требование к компонентам, а не к шрифту.
   Попадает в `peakui-component-standards`.

## 4. Контракт Pro-темы — два прохода

**Проход первый — токены.** Pro-тема это пресет (те же поля из §2) плюс сгенерированный
`variables.css` на своём селекторе.

**Проход второй — внутренности компонентов.** `themes/<id>/components/index.css`: обычные правила
против BEM-классов и `data-slot`. Здесь живёт характер, невыразимый токеном — капслок на лейблах,
хайрлайн-границы на конкретных вариантах.

Тема может объявлять свои токены, **обязательно с префиксом id** (`--brutalism-font-display`), иначе
коллизии между темами.

### Границы

- Pro импортирует `shared/theme.css` ядра. Обратного направления нет — правило экосистемы «ядро не
  знает про Pro».
- Темы Pro лежат в `peakui-pro/packages/styles/themes/<id>/`, потребляются как
  `@import "@peakui-pro/styles/themes/<id>"`.
- **Генератор — публичный экспорт `@peakui/styles`**, а не приватный build-скрипт. Это прямое
  следствие: если Pro генерирует темы, ему нужен генератор ядра. Направление зависимостей при этом
  верное — ядро публикует, Pro потребляет.
- Проход два пишет правила против BEM и `data-slot`, то есть Pro-тема ломается при переименовании
  слота. Это и есть причина, по которой в `api-evolution.md` BEM-классы и `data-slot` объявлены
  публичным контрактом. Связь фиксируется здесь явно.

## 5. Упаковка, переключение, forced-colors

### Переключение

- Селекторы темы: `.<id>, [data-theme="<id>"], :host(.<id>), :host([data-theme="<id>"])`.
- Светлая и тёмная внутри темы комбинируются в одно разрешённое имя (`brutalism-light`).
- `color-scheme: light | dark` объявляется, чтобы нативный UI — скроллбары, каретка, контролы —
  шёл за темой.
- Хук ставит и `class`, и `data-theme` на `<html>`, держит выбор в `localStorage`, понимает
  `"system"`.

### Экспорты `@peakui/styles`

`./css`, `./themes/default`, глоб `./themes/*/*.css` (для Pro), `./base`, `./components/*.css`,
`./utilities`, `./variants`, `./generator`.

### forced-colors

Генератор эмитит **на тему один центральный блок** `@media (forced-colors: active)`, перекладывающий
роли на системные цвета: `--color-surface: Canvas`, `--color-surface-foreground: CanvasText`,
`--color-accent: Highlight`, `--color-accent-foreground: HighlightText`,
`--color-border: ButtonBorder`, `--color-focus: CanvasText`.

Тогда любой компонент, честно использующий токены, деградирует правильно **бесплатно**, а на
компонент остаётся только структурная часть — держать границу видимой (см. `css-authoring.md`).
У эталона поддержки forced-colors нет вовсе.

## 6. Гейты CI

| Гейт                                                        | Что ловит                                                  |
| ----------------------------------------------------------- | ---------------------------------------------------------- |
| Вывод `pnpm tokens:build` совпадает с закоммиченным          | дрейф между пресетом и CSS                                 |
| Проверка контраста проходит на всех пресетах                 | пара, не держащая AA                                       |
| Каждый токен из `theme.css` разрешается в каждой теме        | висящая ссылка на необъявленную переменную                  |
| Каждая тема объявляет полный требуемый набор                 | тема с пропуском — молча падает в пустоту, а не в фолбэк    |
| Ни одного литерального цвета в `components/*.css`             | обход слоя токенов                                         |
| Каждый `var()` в поставляемом CSS объявлен                    | токен, который молча резолвится в пустоту                   |

`attw` запускается с профилем `esm-only` и без CSS-подпутей: пакет действительно только ESM, а
`attw` проверяет типы и JS и про CSS ничего не знает. TS-входы (`.`, `./generator`, `./presets`)
проверяются как обычно.

## 7. Вне объёма

- **UI-билдер тем.** Генератор делает его возможным позже; сейчас не нужен.
- **Набор пресетов.** Ядро везёт `default`. Второй пресет добавляется, когда появится задача, —
  именно чтобы проверить мультитемность на реальном случае, а не на выдуманном.
- **Значения премиальных тем Pro.** Здесь фиксируется только контракт (§4).
- **Миграция существующих компонентов.** Компонентов нет.

## 8. Риски и открытые вопросы

- **Акцент — заглушка.** Архитектура от него не зависит, но первый визуальный обзор его сменит.
  Это ожидаемо и дёшево.
- **Покрытие кириллицы** у Inter и JetBrains Mono заявлено, но под конкретные нужды (например,
  редкие символы в таблицах) проверяется до фиксации.
- **Подбор светлоты в проверке контраста меняет задуманный цвет.** Поэтому генератор обязан сообщать
  о каждой правке: молчаливая коррекция сделает палитру непредсказуемой для дизайнера.
- **`semanticOverrides` — аварийный выход**, и он может стать нормой, если выведенные status-цвета
  систематически не подходят. Если на третьей теме переопределяется всё — выводящая математика
  неверна, и это сигнал, а не повод расширять переопределения.
